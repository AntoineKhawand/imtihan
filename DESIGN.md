# Design — Imtihan

## System (as decided, see `CLAUDE.md` §3/§10)

- Fonts: Fraunces (display serif) + Geist (sans) — never Inter or another generic grotesk.
- Accent: emerald `#1a5e3f`. (Open decision in `CLAUDE.md` §8: could move to terracotta — founder's call, not design's to change unilaterally.)
- Aesthetic: editorial, generous whitespace, no shadcn/generic-component look.
- Must work in both light and dark mode, and at 375px / 768px / 1440px breakpoints (`CLAUDE.md` §14 Definition of Done).

## Audit log

### 2026-09-18 — First static code audit against CLAUDE.md §14 Definition of Done

**Scope:** grep/read-based audit only (no browser/screenshot tools available this session) of `src/components/` and `src/app/` against the token system in `tailwind.config.ts` / `src/app/globals.css`. Nothing was fixed — this is a findings pass; fixes to be dispatched separately.

**Token system baseline (read first, so findings below are judged against what actually exists, not assumed):** the app's dark-mode strategy is CSS custom properties on `:root`/`.dark` in `globals.css` (`--bg`, `--surface`, `--text`, `--text-secondary`, `--border`, `--accent`, etc.), toggled via `darkMode: "class"` in `tailwind.config.ts`. Tailwind's `dark:` variant is barely used (8 occurrences total, in `ExerciseEditor.tsx`, `ExerciseCard.tsx`, `create/generate/page.tsx`) — components are expected to consume the `var(--token)` custom properties via arbitrary-value classes (`bg-[var(--surface)]`, `text-[var(--text)]`) instead. Any component using a raw Tailwind color utility (`bg-white`, `text-gray-500`, `border-gray-100`, etc.) sits *outside* this system entirely and will not respond to the `.dark` class at all.

**1. Dark mode coverage — findings, most → least severe:**

- **`src/app/exam/[id]/page.tsx` (student exam-taking page) — real contrast-failure bug, not just a theming miss.** Line 204 wraps the page in `bg-[var(--bg)]` (correctly dark-aware), but line 263's exercise-statement card is `bg-white p-8 ... text-[var(--text)]` — background is hardcoded white while the text color is the dynamic token that turns near-white (`#fafaf7`) in dark mode. In dark mode this renders as white-on-white/invisible body text for every exercise statement on the one screen a student is actually staring at during a timed exam. Same file, line 206 (`bg-white/80` nav) and line 211 (`bg-gray-100 text-gray-700` timer pill) are hardcoded light too, but self-consistent (won't produce invisible text, just an inconsistent light chrome bar over a dark page). Line 226 (`bg-white` on the tab-blur warning overlay) is on a deliberately red/white alert overlay — lower concern. **This is the highest-priority fix candidate**: it's user-facing (not admin-only), it's a real readability failure not a cosmetic mismatch, and it's the screen a student depends on mid-exam.
- **`src/app/analytics/page.tsx` (lines 263, 318) and `src/app/scanner/page.tsx` (line 233)** combine the shared `.card` component class with a `bg-white` utility in the same `className` (e.g. `"card p-10 bg-white border-none shadow-2xl ..."`). Because `globals.css` loads `@tailwind base; @tailwind components; @tailwind utilities;` in that order, the utilities layer (`bg-white`) wins the cascade over `.card`'s `background: var(--surface)` at equal specificity — same mechanical bug class as **BUG-007** (stale indigo shadows surviving an accent revert because they sat outside the token system), just a background instead of a shadow this time. Net effect: these cards render solid white in dark mode regardless of the `.dark` class.
- **`src/app/globals.css` `.card-elevated`** (lines 161–168) has no `.dark .card-elevated` override — unlike `.card`, which does get a `.dark .card` block right below it (lines 169–177). `.card-elevated` hardcodes `background: rgba(255,255,255,0.85)`. Currently only consumed via `<Card elevated>` in `src/components/ui/Card.tsx`, and the only current call site is `src/app/dashboard/page.tsx`. Low urgency today only because of limited call sites, but it's a primitives-layer gap — any future modal/overlay built with `<Card elevated>` inherits a broken dark mode for free.
- **`src/app/admin/page.tsx` — page-wide, not theme-aware at all.** 119 occurrences of hardcoded `bg-white` / `text-gray-*` / `border-gray-*` / `bg-gray-*` in this one file (confirmed via grep count), zero `dark:` variants, zero `var(--token)` usage. Unlike the exam-page bug above, this won't produce invisible text (everything is internally self-consistent light-on-light), so it's a "doesn't respect the toggle" issue rather than a contrast crash — but it's the single largest concentration of drift in the codebase, and the founder is the one who actually uses this page, plausibly at odd hours. Flagging as lower urgency than the exam page purely because severity (broken vs. merely un-themed) differs, not because volume is small.
- **`src/components/ui/ConfirmDialog.tsx`** (shared primitive in `components/ui/`, so implicitly promises theme-awareness to any future consumer) is fully hardcoded light (`bg-white`, `bg-gray-900/40` overlay, `text-gray-900`, `text-gray-500`, `border-gray-100`, `bg-gray-50`) with no dark variant. Currently only imported by `admin/page.tsx`, so no visible bug yet in a dark-mode-supporting screen — but it's a trap: the moment a non-admin feature reuses this "generic" confirm modal, it will silently break dark mode there too.
- Lower-severity/likely-acceptable, noted but not flagged as bugs: `src/app/print/page.tsx`'s `bg-white text-black` is print-output-only (browser print-to-PDF target, correctly forced to print colors regardless of theme — this is by design, not a bug). `src/app/auth/register/page.tsx` / `auth/login/page.tsx`'s Google sign-in button (`bg-white border-gray-200 text-gray-700`) mirrors Google's own brand button convention (commonly kept white/light regardless of app theme) — worth a founder sanity check but not treating as broken by default. `src/app/opengraph-image.tsx` / `blog/[slug]/opengraph-image.tsx` hardcode colors and `system-ui, sans-serif` — expected/unavoidable for `next/og` `ImageResponse` (edge runtime can't read CSS custom properties or load the project's web fonts without an explicit fetch+embed step), not part of the themed UI surface.

**2. Font usage — one significant, confirmed system-level finding:**

- **The locked-in font system (`CLAUDE.md` §3/§10: "Fraunces + Geist, never Inter or another generic grotesk") has silently drifted.** `src/app/layout.tsx` loads two additional Google fonts — `Nunito` (`--font-nunito`) and `DM_Sans` (`--font-dm-sans`) — alongside Fraunces and Geist. `tailwind.config.ts` wires them up as first-class theme tokens (`fontFamily.heading` → Nunito, `fontFamily.body` → DM Sans), and critically, **`globals.css`'s `body` selector (line 66) sets DM Sans as the primary font for all body text** (`font-family: var(--font-dm-sans), var(--font-geist), system-ui, sans-serif`), with Geist only as a fallback. A `.heading` utility class (`font-family: var(--font-nunito)`) also exists, though it's currently unused outside `globals.css` itself (0 consumers found via grep for `font-heading`/`font-body`/`.heading` class usage in `src/`, aside from an unrelated ID match in `dashboard/page.tsx`). This means: Geist is not actually the operative body font anywhere DM Sans loads successfully — it's a fallback that will rarely if ever be hit. No stray literal `Inter` reference or inline `font-family` violation was found elsewhere (checked all 25 files matching `font-family:`/`fontFamily:`/`Inter` — the rest are `setInterval`/`clearInterval` false-positive matches, transactional-email templates that correctly use system fonts for email-client compatibility, and the two `next/og` OG-image generators noted above). **This is a founder-flag, not something for design to silently revert** — Nunito/DM Sans may be a deliberate, more-recent typography decision that just never made it back into `CLAUDE.md`/`DESIGN.md`, or it may be exactly the kind of undocumented drift `CLAUDE.md` §13 says to catch before it compounds. Either way the fix is a documentation/decision fix, not a code fix design should make unilaterally.

**3. Accent color drift — checked against the BUG-007 precedent, nothing equivalent found:**

- No stray indigo/violet `rgba()` drop-shadows matching BUG-007's old pattern (`rgba(79,70,229,...)`, `rgba(99,102,241,...)`) were found anywhere in `src/`.
- `src/lib/renderContent.ts:251`'s `bg-indigo-600 shadow-indigo-500/20` is the same step-badge color-rotation BUG-007 explicitly documented as intentional and left unchanged — still present, still fine.
- Multi-color usage elsewhere (`bg-indigo-500`, `bg-amber-500`, `bg-orange-500` in `student/dashboard/page.tsx`'s `StatCard` color props; `bg-indigo-100/50` + `bg-amber-100/50` decorative blur blobs in `scanner/page.tsx`'s loading state) reads as intentional data-viz/decorative color-coding, not the primary accent/CTA color drifting off emerald — the actual buttons and primary CTAs checked (`Button.tsx`, admin's filter-active states, exam-page "Submit") all correctly use emerald. Not flagging these as bugs, but noting them here in case a future audit needs the context.
- One open question worth a second look (not urgent): `LandingPricing.tsx:19` and `auth/layout.tsx:19` both use a `bg-violet-500`/`bg-violet-400` decorative blur blob alongside the emerald one. Given the founder's still-open terracotta-vs-emerald accent question (`CLAUDE.md` §8), a second unbranded accent color quietly living in two components is worth a glance next pass, though on current evidence it reads as intentional two-tone decoration rather than drift.

**4. Responsive escape hatches — checked landing, dashboard, create flow, community, admin:**

- No real overflow risks found. All `w-[NNNpx]`/`h-[NNNpx]` fixed-size decorative blur blobs (landing hero, pricing, admin, auth layout, blog, curriculum pages) sit inside `overflow-hidden` ancestor sections (verified `src/app/page.tsx`'s hero `<section>` explicitly, spot-checked the pattern is consistent elsewhere) and are `pointer-events-none`/absolutely positioned, so they don't force layout width at 375px.
- `min-w-[NNNpx]` usages (`community/page.tsx`'s search input at `min-w-[200px]`, `ExerciseCard.tsx`'s `min-w-[120px]`/`min-w-[160px]`/`min-w-[28px]`/`min-w-[32px]`, `create/generate/page.tsx`'s `min-w-[160px]`) all live inside `flex ... flex-wrap` containers, so at 375px they wrap to a new line rather than overflowing horizontally. `admin/page.tsx`'s `md:w-[320px]` search input is `w-full md:w-[320px]` — full-width below the `md` breakpoint, not a fixed 320px floor on mobile.
- Nothing found that looks like it would force horizontal scroll at 375px in the screens most likely to be opened on a phone (landing, `/create/*`, `/dashboard`, `/community`).
