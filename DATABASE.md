| `users/{uid}` | `UserProfile` (`src/types/user.ts`) | Teacher/school-admin accounts. Self-owned read/write. |

Teachers get school-scoped `list` access (BUG-026, fixed on disk 2026-09-18, not yet deployed). **Caveat (2026-09-18 second review): the "teacher's own school" side of the scope is `users/{uid}.school`, a free-text field any signed-in account can set to any value — see decisions log below. ## Known gaps / decisions log

- **2026-09-18 — BUG-026**: `firestore.rules` never granted teachers `list` access to `student_profiles`/`student_attempts` at all — the `/teacher/students` feature has been non-functional since it shipped (`51e4c7f`). Fixed on disk: school-scoped `list` rules plus two new composite indexes. **Not yet deployed** — needs `firebase deploy --only firestore:rules,firestore:indexes` and ideally a review/emulator test first, since it's a security-rule change gating real student data.

- **2026-09-18 — BUG-026 second review (database team, independent of the author of the original fix)**. Reviewed `git show 51ec045 -- firestore.rules firestore.indexes.json`, the calling code (`src/app/teacher/students/page.tsx`), the full `firestore.rules`, and the two new composite indexes in `firestore.indexes.json`. Going through the four checks:

  1. **`student_profiles` `list` rule vs. the app's query** — mechanically correct. The app runs `where("schoolName","==",teacherSchool)` + `orderBy("createdAt","desc")`; the rule's `resource.data.schoolName == requesterProfile().school` is the textbook Firestore pattern for scoping a `list` query to a caller-derived value (Firestore's rule evaluator statically requires the query to carry a matching equality filter before it will run at all — an unfiltered or wrong-school query is rejected outright, not silently returned empty). So yes, it genuinely prevents any query that isn't already constrained to `schoolName == requesterProfile().school` specifically. **But** see finding below — the value it's scoped to is not itself trustworthy.

  2. **`student_attempts` `list` rule's nested `get()`** — only half-closes the hole it describes. The commit message frames the fix as "scoped by the target student's real school, not their own claim." Walking through it: the rule is `requesterProfile().school == get(student_profiles/$(resource.data.userId)).data.schoolName`. The right-hand side (target's real school, looked up from the target's own profile doc, keyed off the `userId` the query itself declares) is indeed unspoofable by the caller — good, this correctly replaces "trust an arbitrary uid parameter" with "look up what that uid's school actually is." **But the left-hand side, `requesterProfile().school`, is exactly the same self-reported field the commit's own reasoning warns about** — and it turns out `users/{uid}.school` is a **free-text field any signed-in account can set to any string**, with zero verification anywhere in the stack:
     - `src/app/bank/page.tsx` (`handleSaveSchool`) lets any signed-in user `updateDoc(users/{uid}, { school: name })` with an arbitrary typed string — by design, its own toast copy says *"Colleagues with the same school name will now share your bank"*, i.e. `school` is an intentional honor-system matching key for the (lower-stakes) `schoolBank` feature, not a verified identity claim.
     - `src/app/auth/register/page.tsx` never even validates `school` against anything at signup (it isn't collected there at all — it's set later via the bank page).
     - `firestore.rules`'s own `users/{userId}` rule is unconditional self-write (`allow read, write: if request.auth != null && request.auth.uid == userId`) with no field-level restriction, so `role` and `school` are both freely editable at any time, by anyone, forever.
     
     Concrete walkthrough (as asked): register any new account via the normal teacher signup flow (no field-editing/spoofing tricks needed at all) → go to `/bank` → "Set your school name" → type in another real school's exact name → `role` is already non-`"student"` from registration and `school` now equals the target. Now:
     - `query(student_profiles, where("schoolName","==","<target school>"))` passes the `list` rule → full roster (names, emails, uids) of every student at that school.
     - For each returned `uid`, `query(student_attempts, where("userId","==",uid))` passes the `list` rule too, since `get(student_profiles/uid).data.schoolName` is genuinely `"<target school>"` and now matches the attacker's self-declared `requesterProfile().school`. → complete per-subject practice/attempt history for every student at that school.
     
     A student account can do the same thing by additionally editing their own `users/{uid}.role` away from `"student"` first (also unrestricted). So: **the BUG-026 patch correctly fixes the bug it was written for (teachers had zero list access, feature was fully broken) and is textbook-correct Firestore rule syntax, but it does not achieve real cross-school data isolation**, because there is no field anywhere in the schema that represents a *verified* teacher-school affiliation — `users/{uid}.school`/`.role` are self-declared by design (the same field doubles as the `schoolBank` "honor system" matching key) and self-writable with no restriction. This is pre-existing, not introduced by this commit, but this commit is the first place the app relies on that field to gate *student PII* (names, emails, and full quiz-performance history) rather than optional shared exercise content — that's a materially higher-stakes use of an already-known-weak field.

  3. **Other collections with the same shape** — the two new `list` rules from this commit are themselves the instances of this shape (self-writable `users/{uid}.role`/`.school` as the sole caller-side authorization key). The pre-existing `schoolBank` read/write rules use the same self-declared `school`/`schoolSlug` field as their matching key (see BUG-013), same root cause, but lower stakes since it gates optional shared exercise content between presumed colleagues, not personal student data, and the product's own copy treats it as an intentional convenience/honor-system feature rather than an access-control boundary. Flagging as the same root cause rather than a separate bug to fix under this ticket.

  4. **Indexes** — both correct and match the query shapes. `student_profiles`: `schoolName ASC, createdAt DESC` matches `where("schoolName","==",…) + orderBy("createdAt","desc")`. `student_attempts`: `userId ASC, timestamp DESC` matches `where("userId","==",…) + orderBy("timestamp","desc")`. Both are `queryScope: COLLECTION`, correct since both collections are top-level, not subcollections. No gap here (unlike BUG-013).

  **Verdict: do not deploy as-is without a decision from the founder.** I did not edit `firestore.rules` myself — a real fix needs a non-self-writable trust anchor for "this account is a verified teacher at school X" (e.g. Firebase custom claims set server-side via the Admin SDK at a controlled onboarding/invite step, an email-domain allow-list, or admin approval), which is new server-side infrastructure and a product decision (how much verification before launch), not a rules tweak. Making `users/{uid}.school`/`.role` immutable-after-create in rules was considered and rejected: it would break the legitimate, currently-shipped `/bank` "set your school name later" flow and the `schoolBank` sharing feature, without actually closing the hole (an attacker can just declare the target school correctly at account-creation time instead of editing it in afterward). Added to Open Questions below for the founder — this is exactly the class of cross-school-sharing-scope / privacy-adjacent decision that's the founder's call, not mine to unilaterally patch.
- **Pattern to watch**: BUG-011 (rules never deployed, 4 months of broken client reads), BUG-013 (missing composite index), BUG-026 (missing rule entirely) are the same underlying failure mode — the deployed Firestore state silently drifts from what the repo assumes. A periodic "does the live project's rules/indexes actually match `firestore.rules`/`firestore.indexes.json`" check is worth doing, not just a code review.
- **Deploy guardrail**: per `CLAUDE.md` §12/§15, actually deploying rules or indexes to Firebase is the founder's action, not something any agent should run.

## Open questions for the founder

- **How should a teacher's school affiliation be verified, if at all, before we gate student PII (rosters + full quiz history) on it?** As of 2026-09-18, `users/{uid}.school` and `.role` are free-text, self-editable fields with zero verification anywhere in the stack (the `/bank` page even advertises `school` as an honor-system matching key for the `schoolBank` feature: "Colleagues with the same school name will now share your bank"). The BUG-026 fix for teacher access to `student_profiles`/`student_attempts` (see decisions log above) is gated entirely on this field, meaning any signed-in account can see another school's full student roster and per-student practice history just by typing that school's name into their own account settings — no exploit or field-spoofing trickery required, just normal use of an existing feature. Options range from "accept the risk pre-launch since the app isn't public yet" to "require Firebase custom claims set server-side at a controlled invite/verification step" to "email-domain allow-list per school." This is a privacy/business-risk call, not a technical one — flagging rather than deciding.
